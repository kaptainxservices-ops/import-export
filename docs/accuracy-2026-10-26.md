## What was wrong, and what changed

**Extraction** (`app/brain/tables/`, `app/brain/normalise/product.py`)
- `Total_qty` was one word to the header reader. Underscores now separate words.
- Capacity `128G`, `256G`, `1T` was not read; it is now, in a column and in a description
  (`5G`/`4G` cannot match — only real storage sizes take a bare G).
- `Grade`, `MFR` and `SPEC` columns are now read (grade, brand, market).
- A bare `Price` beside `Euro`/`USD$` columns took the currency of `USD$`. The price
  column's own header now decides; when it names none, the ratio to the labelled
  columns identifies it (985 beside €1172 and $1330 is sterling), and failing that the
  labelled column is used.
- Titles, file names and section headings saying *incoming / in transit / ETA* mark the
  rows `availability = incoming`, with the ETA text kept.
- Huawei is no longer filed as Honor; *Galaxy Watch Ultra* is no longer an Apple watch;
  a brand column (`MAKE`) is preferred over guessing from the description.

**Identity** (`ProductSpec.identity_key`, migration 0015)
- Grade, market and availability are now part of what makes a lot. The same model in
  AA and C, India-spec and EU-spec, warehouse and incoming, are separate offers.
- Two lines of one lot on the same sheet at the same price are added together (two
  batches). Two lines at different prices still keep the first.
- A sheet that only totals another sheet of the same email is left out
  (`app/brain/summary.py`).

**Matching** (`app/brain/matching.py`, `app/brain/normalise/canonical.py`)
- Every line gets a canonical model key — `SAM S23`, `Samsung Galaxy S23` and
  `Galaxy S23 5G` are all `samsung:s23`; `S24+` is `s24plus`; `Z Flip7 FE` is
  `flip7fe`; `IP15PM` is `iphone15promax`. Variant words (Pro, Max, Ultra, FE, Plus,
  Lite, Edge…) are never removed, so an S23 never meets an S23 Ultra. 27 must-match and
  29 must-not-match pairs are in `tests/test_canonical.py`.
- Grade, market, RAM, 4G/5G, Wi-Fi/cellular and Enterprise Edition are compared when
  both sides state them; a difference is a near miss that says what differs.
- A buyer who names no colour takes any colour.
- Market codes are compared by market: INDIA meets HN/A and HX/A, EU meets ZD/A and
  QN/A. The market inside an Apple part number (MFYP4**ZD**/A) is read.
- A supplier's unlabelled line beside a labelled 5G line of the same model is the 4G
  phone (Galaxy A17 A175 vs A176).
- Lots listed without a price are offered (as a lead, ranked last, never inside a
  combination) instead of being invisible.
- Every option says when the lot is incoming, graded, or a particular spec.

**The model, only where rules cannot decide** (`app/brain/resolve_models.py`, migration 0016)
- After a list is applied, a wording whose canonical key differs from one already on
  the board *only by descriptive words* (never a number, never a variant word) is put to
  the configured LLM, batched, once. The answer — yes or no — is stored in
  `model_equivalences`; matching reads it on every board load. A human row is never
  overwritten. With no model configured, nothing changes.

## Deploy — in this order

1. Supabase SQL editor: run `supabase/migrations/0015_grade_region_availability_in_identity.sql`,
   then `0016_model_equivalences.sql`. **Before deploying the code**: the board query now
   selects `availability`, and would fail against a database without it.
2. Deploy the backend to Render as usual.
3. Deploy the frontend (grade, spec and an *incoming · ETA* tag now show on each row).
4. Re-send Whitehawk's 26-10 email (or wait for tomorrow's). Lots whose identity moved —
   graded Samsung lines, `128G` capacities — are inserted under the new key; the old
   rows close when the list is complete, as with any list.

## The LLM setting

Provider-agnostic, chosen in `.env` / Render environment:

- **Groq** (what `.env` has today): `LLM_BASE_URL=https://api.groq.com/openai/v1`
- **xAI Grok**: `LLM_BASE_URL=https://api.x.ai/v1`, `LLM_API_KEY=<xAI key>`,
  `LLM_EXTRACT_MODEL` / `LLM_CLASSIFY_MODEL` = the model name from the xAI console.
- **Claude** later: set `ANTHROPIC_API_KEY`; it takes precedence automatically.

The resolver uses the `extract` model. Whatever is configured, it can only answer the
questions code allows it to be asked.
